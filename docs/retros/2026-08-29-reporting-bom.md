## The shape of the run

All nine steps ran. Step 1's plan committed to a real, novel architectural decision up front — the report bypasses aggregate hydration entirely and pushes filtering/pagination/sorting into SQL, and `Bom`/`StandardBom` clone the extra fields the report needs rather than joining at query time — and named the exact wire contract (`POST /boms/report`, `GET /boms/report/filter-options`, `GET /boms/:id`, field names included) before dispatching QA and backend in parallel, applying the previous run's own suggested fix for that exact friction. That contract held with zero mismatch this time — a real improvement over the prior run.

Both parallel dispatches (steps 2 and 3) were killed by the first rate-limit reset before producing anything; both were re-dispatched fresh with the same pinned contract. Backend's fresh dispatch (`FindComponentByNameQuery`/`FindMaterialByNameQuery` groundwork was still ahead of it at this point — it hadn't started) built the report reads cleanly; QA's fresh dispatch finished the full automation, `--dry-run` clean. Frontend (step 5) was one uninterrupted dispatch. Step 6 (guardrails) is where this run diverged sharply from the previous one: a first `run-guardrails` round surfaced 13 failures, all traced (by the orchestrator, via curl and reading source) to a single missing backend capability — `ProductCompositionFactory` couldn't reuse a material/component name across two components of the *same* product-registration request, which the feature's own realistic background data needed. That fix uncovered a second, deeper instance of the identical gap one level up (reuse *across different* products), which uncovered a third, unrelated bug (`registeredAt` was stamped by Postgres' own `now()`, never the injected test `Clock`), which uncovered a fourth, narrower bug (a missing navigation step in one scenario's own automation, previously masked by the other three). Four routed fixes in sequence, each one only visible once the previous one was fixed — not four independent failures found at once. Step 7 was a read-only diff review (grepped for debug leftovers; none found). Step 8 committed and pushed without a confirmation stop. This file is step 9.

## Where the step-1 plan was wrong

The plan got the wire contract and the "bypass aggregate hydration" architecture right — no contract mismatch this run, unlike last time. What it didn't anticipate, because nothing in the plan asked the question, was whether the **existing** `products` module could actually satisfy the realistic composition the feature's own background table describes: the same raw-material name ("مسی"/Copper) used by two different components of one cable, and the same component/material names reused across *different* cable products. Nothing about pagination or the read model predicted this — it's a write-side gap in a module built in an earlier run, invisible until fixture data exercised it for the first time. The plan's own "decisions expensive to reverse" section named the read-model shape and the clone-vs-join call; it had no mechanism for "does the write side already support what this report's test data needs," because that's not a question step 1's own template asks. This is a different category of planning gap than the previous two runs' contract mismatches — worth naming as its own class rather than folding into "the contract wasn't pinned enough," since the contract *was* pinned correctly here and the problem still occurred.

## Guardrails

**Round 1**: 13 of 17 scenarios in this feature failed, all on the same `TypeError: Cannot read properties of undefined (reading 'forEach')` — `POST /products` 409ing on a repeated material name within one request. Routed to backend-engineer with the exact file, method, and fix scope (a request-local name→id cache in `ProductCompositionFactory`). Fixed, unit-tested, verified live in one dispatch.

**Round 2** (orchestrator's own re-run, not a full guardrails pass): a *new* failure appeared once the first was fixed — `component-name-already-exists` registering a *second*, unrelated product that also needed "مغزی"/"آلومینیوم". Checked `registring-product.feature` in full first (no scenario forbids this) before committing to the fix, then routed to backend-engineer: extend the same factory to check a global `Find*ByNameQuery` before creating, mirroring the `GetProductQuery`/`GetStandardBomByMiCodeQuery` narrow-crossing pattern already established twice in this codebase. Fixed, unit-tested, verified live.

**Round 3**: date-range filters returned empty results even for wide, obviously-matching ranges. The orchestrator ruled out a QA/frontend Jalali-timezone mismatch directly (read both hand-rolled converters; they agree) before looking further, then found via direct curl that a freshly-registered BOM's `registeredAt` was today's real date despite the test clock being frozen to 2024 — `createdAt @default(now())` reads Postgres' own clock, bypassing the injected `Clock` port entirely. Routed to backend-engineer with the live repro already in hand; fixed (stamped explicitly from `Clock` at insert time, applied to `StandardBom` too since it had the identical latent gap), unit-tested, verified live.

**Round 4**: one scenario left, failing inconsistently (sometimes a 30s "button not found," sometimes a 5s "content not found" after a successful click). The orchestrator formed a specific, precedented hypothesis (a nested `overflow-x: auto` table clipping the action button, the same class of bug an earlier run in this same codebase had already hit and fixed for a dialog) and routed it to qa-engineer with that hypothesis stated plainly as a hypothesis, not a diagnosis. QA checked it directly against the real page (no horizontal overflow at the tested viewport) and found the actual cause instead: the scenario's own `When` step never navigated to the report page at all, unlike every sibling scenario in the same feature, which all get that navigation from a preceding `Given`. Fixed, verified green three consecutive standalone runs plus the full feature file.

**Round 5** (the real, from-scratch `make run-guardrails`, after all four fixes): fully green on the first attempt — 174 scenarios, 17/17 on this feature, no regressions anywhere else, `EXIT:0` confirmed correctly this time (see Friction).

Five rounds total sounds like it blew the three-strike cap, but the cap is about **routed fixes that don't land**, not about how many distinct bugs a feature surfaces in sequence — every one of these four routed fixes worked correctly on its first real attempt; each new failure was a *different* bug the previous fix's success had simply uncovered. Worth flagging for whoever next reads this file's own three-strike rule: it doesn't have language for "a chain of four correct, sequential fixes on one feature," and this run is a clean example of why that's a different situation than three failed attempts at the same bug.

## Friction

- **The orchestrator masked real failures behind a false "exit code 0" twice**, by piping `make lint`/`make lint-architecture` through `tail` in the same command (`make ... | tail -20 && make ... | tail -20`) and then reading the *pipe's* exit code, which is `tail`'s, not `make`'s — both checks had actually failed (`Error 130`, `Killed`) while the wrapping shell reported success. Caught only because a later, independent lint run (this time redirecting to a file with an explicit `echo "EXIT:$?"` after the bare command, no pipe) showed real errors. Section this belongs to: any future "let me verify directly" step — never pipe a `make` invocation whose exit code will be checked through anything, redirect to a file and check `$?` explicitly instead.
- **A backend-engineer dispatch (the cross-product component/material reuse fix) reported "standing by" / "still waiting" as its own turn's final answer, repeatedly, across at least four separate task-notifications**, each with different (and not obviously cumulative) token/tool-use totals, before ever producing a real completion report. The work it described in the meantime (visible via a live `CLAUDE.md` diff and, independently, the orchestrator's own direct `make run-unit-tests`/`make lint` runs) was correct and complete — this was a reporting problem, not a work problem — but it made "is this agent actually done" genuinely hard to tell from its own output alone, and the orchestrator had to fall back to verifying everything itself rather than trusting the dispatch's own status.
- **The orchestrator made one genuinely wasted tool call** — an `Agent` dispatch with the literal prompt `"placeholder"`, apparently a stray/duplicated tool invocation — burning a small amount of budget on an agent that correctly replied asking what the actual task was. No real cost beyond the one dispatch, but worth naming since "don't spawn agents without a real task" is exactly the kind of thing this file exists to catch.
- **A host reboot mid-run** (Docker containers gone, background shell notifications arriving as "stopped, no completion record" rather than real results, `uptime` confirming a ~30-minute-old host) cost real orchestrator time re-establishing state (checking `docker ps`, `git status`, re-running checks one at a time) before productive work could resume. Nothing in `develop-feature` currently says what to do here, and arguably nothing should — this is infrastructure instability, not a process gap — but it's worth naming plainly rather than folding into "guardrails took extra rounds," the same reasoning the previous retro gave for account-level rate limits.
- **What worked well, worth keeping**: pinning the exact wire contract in step 1 and quoting it verbatim into both parallel dispatches (the previous retro's own suggestion) produced zero contract mismatches this run, a clean contrast with the prior run's `standardBomId`/`standardBomMiCode` guess-mismatch. Also: routing a *hypothesis* to a subagent explicitly labeled as a hypothesis ("I ruled out X, here's my best guess, verify against the real page before committing to a fix") let qa-engineer disprove it quickly and find the real cause, rather than either agent wasting a round chasing a wrong diagnosis stated as fact.

## Suggested improvements

1. **Add to `develop-feature`'s step 6 guidance**: *"When verifying a `make` target's exit status directly (not through the `Agent` tool's own reporting), never pipe the command through `tail`/`head`/`grep` before checking `$?` — the pipeline's exit code is the last command's, not `make`'s, and this can silently report success for a real failure. Redirect to a file and check `$?` explicitly instead: `make target > file 2>&1; echo \"EXIT:$?\"`."* *Observation source: "Friction," first bullet — this cost real time twice in one run.*

2. **Add a line to step 1's "decisions expensive to reverse" checklist**: *"If the feature's own background/example data implies a composition or reuse pattern (the same name shared across two entities, the same entity referenced twice), check whether the write-side module that data would exercise already supports it — a report/read-side feature can be blocked by a write-side gap in an already-shipped module, and that gap won't surface until real fixture data is built, which may be several steps into the run."* *Observation source: "Where the step-1 plan was wrong" — this run's dominant finding, and a materially different failure mode than either prior run's contract mismatches.*

3. **Add a note to step 6's three-strike-cap language**: *"A chain of routed fixes where each one succeeds and uncovers a new, different failure is not the same situation the cap exists to stop — that cap is for repeated failed attempts at the *same* bug. Use judgment: if every routed fix so far has landed correctly on its first try, continuing past three total fixes on one feature is reasonable; three *failed* attempts at one specific bug is what should trigger stopping and reporting."* *Observation source: "Guardrails" — this run's five-round chain would read as a cap violation without this clarification, when in fact it was four consecutive first-try successes.*
