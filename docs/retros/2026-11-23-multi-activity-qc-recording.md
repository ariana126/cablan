## Where the step-1 plan was wrong

- The plan said "resend = same submissionId → answered, never duplicated". The book review showed
  that a resend carrying a **different** tracking number (or equipment/performer) under the same id
  would silently split one «نوبت» across two tracking numbers. The contract grew a 409
  `qc-submission-mismatch`, which the frontend had to learn (and which made it lock the tracking
  number once sent). The plan should have stated what a resend with changed content means.
- The plan put the retirement check first ("equipment-level checks first"). For a resend whose
  first sending succeeded, that turns "your work was recorded" into a 409 after a later retirement.
  Order became: 404 → earlier records of the submission → retirement only if something is left.
- The plan said the existing single-activity record dialog might stay; the frontend deleted it,
  since the checklist subsumes it (the single-record endpoint stays for the API).

## Friction

- **Worktree-isolated git commands** (How this works): compound shell lines mixing `git` with
  heredocs/`cd`/pipes were refused by the harness; every git call had to be a plain single command,
  and file writes had to go through the Write tool.
- **Disk** (~2 GB free throughout): the frontend agent skipped `make lint-accessibility` and ran the
  `/qc-inspection` audits from another image instead; the backend agent built and then had to remove
  a private image. Step 6's "local cheap checks" and agents' own verification compete for that disk.
- **Shared Docker images across worktrees** (step 4/6): a schema change in a worktree leaves the
  shared backend image stale for every other target (`generate-swagger`), and
  `run-integration-tests` rebuilt the shared *test* image from this worktree.
- **Step 3 ordering**: waiting for the book review before infrastructure would have cost a full
  review round-trip of wall clock; running it in parallel worked because its findings were
  additive.
