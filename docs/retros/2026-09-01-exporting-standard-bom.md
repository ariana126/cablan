## Where the step-1 plan was wrong

This is the section this run actually has something to say, unlike its sibling (which reported the plan holding with zero deviation).

**The plan assumed filter parity between the two sibling report pages without checking, and that assumption was false.** The plan stated the standard-BOM export would reuse "the same filter shape `POST /standard-boms/report` already uses" — true as far as it went, but it never verified that the *set of filterable fields itself* matched what the daily-BOM sibling already had. It didn't: `reporting-standard-bom.feature`'s own filter scenario outline (an already-shipped, unrelated-to-this-run feature) only ever tested برند، فعال، نام جز، نام محصول as filterable — "کد MI" was never built, on either the backend (`StandardBomReportFilters` had no `miCodes`) or the frontend. But `exporting-standard-bom.feature`'s own filtered-export scenario — the very feature this run was building — names "کد MI" as its filter field, exactly mirroring how the daily-BOM export's equivalent scenario uses "کد MI" there (where it *does* already exist, as `standardBomMiCodes`). The plan's own "mirror the `boms` module's export" framing quietly imported an assumption that the two sibling report pages were already at parity on filterable fields, and nobody checked until `make run-guardrails` actually ran the scenario and it timed out waiting for a filter button that doesn't exist. This is exactly the kind of thing step 1 exists to catch, and in this run it didn't — the check (open `reporting-standard-bom.feature`, compare its filter Examples table against what the export scenario needs) would have taken under a minute and would have let the fix land inside the original backend/frontend dispatches instead of costing a whole extra guardrails round.

## Guardrails

- **Round 1 `make fix-violations`**: clean immediately, no lint issues (unlike the sibling run, which hit a stale-Docker-volume false failure here).
- **Round 1 `make run-guardrails`**: reported exit 0 to me at first — **wrongly**. I piped the command through `tail -400` for display (`make run-guardrails 2>&1 | tail -400`), and a pipeline's exit status is its last stage's, so I was reading `tail`'s exit code, not `make`'s. The actual run had two failures: (1) `خروجی اکسل آنالیز های استاندارد`, 1 of 4 scenarios broken — `Timeout 30000ms exceeded` waiting for `role=button[name="فیلتر کد MI"]`, i.e. exactly the missing filter described above; (2) `ثبت چند جز برای یک محصول` (`bom-registration`, entirely unrelated to this feature) — a component-name assertion mismatch that looked like test-data flakiness, not something any of this run's three agents' diffs could plausibly cause.
- Routed the real gap in two parts, both requiring a fresh `Agent` dispatch rather than a `SendMessage` resume — see Friction. **backend-engineer**: add `miCodes` to `StandardBomReportFilters`/DTO/`filterOptions`/`toWhereInput`, threaded through both `report()` and `export()`. Self-verified with a live curl round-trip against the running test stack (filtered vs. unfiltered vs. empty-array-means-match-nothing) before reporting back. **frontend-engineer**: add a "کد MI" filter button to `standard-bom-reports-page.ts`, at parity with the daily-BOM page's own `CHECKBOX_FILTER_FIELDS` entry for the same field. Self-verified with a real browser pass (opened the filter, deselected the only value, confirmed "هیچ آنالیز استانداردی یافت نشد", reselected, confirmed the row came back).
- **Round 2 `make run-guardrails`**: this time captured properly (redirected to a log file, exit code checked explicitly via a `Monitor` wait on an `EXIT:` marker rather than trusting a piped `tail`). Green: 174/174, including all 4 `خروجی اکسل آنالیز های استاندارد` scenarios and `ثبت محصول` (formerly the "broken" flaky one) at 15/15 — confirming that failure really was incidental, not a regression from this run's changes.

So: two real guardrails rounds, one genuine feature gap (the missing filter) surfaced and fixed, one red herring (flaky unrelated test) correctly not chased.

## Friction

- **Piping `make run-guardrails` through `tail` masked a real failure as a pass — and this is a repeat of exactly the same mistake from the sibling run's own retro,** which had already named this as friction and proposed a fix. That proposal (write to a suggestions section, not into the instructions) never reaches the next invocation of this skill automatically, so the same orchestrator (me, this session) made the identical error twice in a row within a few hours. This is the single most concrete, actionable finding in this file — see Suggested Improvements.
- **Both agents dispatched earlier in this same run — backend-engineer (`a8b986734251128a4`) and frontend-engineer (`a58ebfb89b9ef10b9`) — were unreachable via `SendMessage`** ("No transcript found for agent ID") when I went to route the guardrails fix to them. This is the documented "a dispatch can be killed outright" scenario from "How this works," but it's notable that it hit *both* agents from the same run, not just one — I followed the rule correctly each time (tried `SendMessage` first, fell back to a fresh `Agent` dispatch with explicit on-disk context only after the resume failed), so this wasn't a process error on my part this time, just a cost the run had to absorb twice.
- Recovering the actual failure detail after round 1's masked "pass" required an extra targeted re-run of just the one feature file (`docker compose exec app npx cucumber-js specs/bom-reporting/exporting-standard-bom.feature`), because the piped `tail -400` had already discarded the earlier lines of the log that held the real stack trace — compounding cost from the same root cause above.

## Suggested improvements

- **Observation**: `make run-guardrails` piped through `tail` reported a false pass, identically to the sibling run earlier the same session (Guardrails, Friction). **Section**: "Steps → 6. Guardrails." **Concrete change**: add this sentence directly to the step: "Never pipe `make run-guardrails` or `make fix-violations` through `tail` for display — a pipeline's exit code is its last stage's, not `make`'s, so a real failure will read as exit 0. Redirect to a file instead (`make run-guardrails > guardrails.log 2>&1; echo EXIT:$? >> guardrails.log`) and read the file separately, or capture `${PIPESTATUS[0]}` explicitly before trusting the result."
- **Observation**: two agents dispatched earlier in the same run were both unreachable when routing a later guardrails fix (Friction). **Section**: "How this works," the "A dispatch can be killed outright" bullet. **Concrete change**: append "This can happen to more than one dispatched agent in the same run — a second `SendMessage` failure right after the first is not a signal to investigate differently; apply the same fresh-dispatch fallback each time, independently."
- **Observation**: the plan assumed filter-field parity between two sibling report pages without checking, and the assumption was wrong (Where the step-1 plan was wrong). **Section**: "Steps → 1. Understand the feature and plan the slice." **Concrete change**: add "When the feature being developed is an explicit sibling of an already-shipped one (same Gherkin shape, different aggregate — e.g. a daily-BOM feature and its standard-BOM twin), check that every field/filter the new feature's Gherkin names by name already exists on the sibling's own already-shipped implementation, not just that the *shape* of the request/response matches. A field present in one sibling's UI but not the other's surfaces only in step 6 otherwise, after three agents have already built against the false assumption."
