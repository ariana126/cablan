## Where the step-1 plan was wrong

The plan's HTTP-surface guess (`POST/PATCH/DELETE/GET /boms`, plus a new `GetStandardBomByMiCodeQuery` on the already-shipped `standard-boms` module) held exactly — backend built precisely that, unprompted about the query's own shape beyond "add one mirroring `GetProductQuery`." That part worked as intended, same as the previous retro's finding for `registring-standard-bom.feature`.

What the plan got right in prose but never nailed down in dispatch is the actual **wire contract** for `POST /boms` — the plan described the daily BOM as "driven from a standard bom, looked up by MI code" but the QA dispatch (written before backend had a single line of the DTO) never received an exact field name. QA's own `registerRequestBody()` sent `standardBomId` — reasoning by analogy from `StandardBom.productId` being "a real field on the aggregate," per its own comment — while the backend, dispatched moments later, independently settled on `standardBomMiCode` (the actual lookup key, per the design the orchestrator itself specified in the backend dispatch). Neither agent was wrong given what it had in hand; the orchestrator's own two dispatches simply described the same design in prose without ever committing to a single, shared field name either could point back to. This is the direct cost of running steps 2 and 3 in parallel: with no live contract yet, at least one contract-shaped guess was always going to land wrong, and it did.

The second bug from round 1 — QA's `mat-option` locator doing an exact match on just the MI code (`"0001"`) against a real rendered option text of `"0001 — لگراند"` — is a plain repeat of last run's own documented friction (`2026-08-27-registring-standard-bom.md`'s suggestion #2: point frontend-engineer at QA's `ASSUMPTION`-tagged locators before it designs markup). That suggestion was written down but never merged into this skill file, and the orchestrator's own frontend dispatch this run made the identical omission — it described the desired behavior in prose and pointed at `standard-boms` as a template, but never told frontend-engineer to read `screenplay/ui/boms-page.ts`'s `ASSUMPTION`-commented locators first. The option-label mismatch is exactly the class of bug that suggestion exists to prevent.

## Guardrails

**Round 1** (`make run-guardrails`): every check up through `lint-accessibility` passed on the first try. `run-acceptance-tests` failed: 13 of 16 scenarios in this feature. All 6 UI-driven "register" scenarios failed on a 30s `scrollIntoViewIfNeeded` timeout selecting the standard-BOM option; all 7 edit/delete-related scenarios failed on a 5s timeout waiting for an edit/delete button that never appeared. The orchestrator diagnosed both directly rather than guessing which project to route to: a direct `curl` round-trip against the live backend test stack proved `POST /boms` genuinely rejects `standardBomId` (400, `forbidNonWhitelisted`) and accepts `standardBomMiCode` (201) — explaining why every `Given`-registered daily BOM used by the edit/delete scenarios silently never existed, since `RegisterBomAndRememberIt` never checked the response status before remembering a bom built from `body.id === undefined`. A throwaway Playwright script driven from inside the `acceptance-tests` container, against the same live stacks, reproduced the real `mat-option` text and proved both the backend and the frontend worked correctly end to end — isolating both failures to automation.

Routed to **qa-engineer** with the exact field name, the exact selector fix strategy, and the reasoning already spelled out. That dispatch fixed both correctly (`standardBomMiCode` in `registerRequestBody`; `By.cssContainingText('mat-option', ...)` in place of an exact `By.role` match, with a documented reason `By.role`'s `[name=]` can't do a substring match the way `page.getByRole()` can) — then was killed by the second rate-limit reset while investigating a *third*, self-discovered failure the orchestrator's own routing message hadn't mentioned. Re-verifying against the live stacks after the reset showed 14/16 passing, both remaining failures on the same step: a raw-material-weight validation error the frontend deliberately renders as a root-level form error (per `server-errors.ts`'s own comment — no reliable nested field path for a composition error), which QA's assertion only checked as a per-field `<mat-error>`. Routed to a **freshly dispatched** qa-engineer (the killed one's transcript was gone) with that diagnosis already made. It applied the fix, then — through its own empirical probing (`getBoundingClientRect`/computed-style checks against the live page) — found a second, genuinely latent bug the orchestrator had missed: the existing "check both error surfaces" helper it was told to reuse verbatim was itself checking a field error by `.isVisible()` rather than by presence, and a real, correctly-rendered `mat-error` scrolled outside `mat-dialog-content`'s clipped scrollport reports as not-visible to Playwright's occlusion check. Fixed by switching the field-error half of that check to `formErrors().count() > 0` (matching what the already-passing order/tracking-number assertions rely on) OR'd with the root error's `.isVisible()`.

**Round 2**: full `run-guardrails` green, including 16/16 on this feature (run twice by the fixing agent for confirmation) and no regressions across the other 158 scenarios in the suite. Three routed fixes across the whole run (two bugs in the first routing, one in the second), zero repeats of the same bug — nowhere near the three-strike cap.

## Friction

- **Parallel-dispatching steps 2 and 3 traded wall clock for a guaranteed contract mismatch.** The skill lists QA and backend as sequential steps for a reason: QA has nothing but the plan's prose to build a request body from until a real DTO exists. Worth a line in step 2 or 3 of `develop-feature`: *"If QA and backend are dispatched in parallel (a legitimate wall-clock optimization), the step-1 plan must pin the exact field names of every new request/response shape it introduces — not just which endpoints exist — since neither agent can see the other's guess before guardrails."* This run's `standardBomId`/`standardBomMiCode` mismatch is the direct, reproducible cost of skipping that.
- **The previous retro's own suggestion #2 (point frontend-engineer at QA's `ASSUMPTION`-tagged locators) was written down but not applied**, and the identical class of bug (an exact-match locator against markup that didn't exist yet) recurred this run for the same reason. A *suggestion* in a retro file is not a fix until it's actually merged into the skill's step 5 template; this is the second data point in a row for the same gap.
- **The previous retro's suggestion #3 (dispatch fresh with full context when a routed agent is unreachable) was independently re-derived by the orchestrator this run**, without having read that file first — the orchestrator hit the identical failure mode (a killed agent, an unresumable transcript) three separate times this run and converged on the same strategy each time by necessity. That convergence is itself evidence the suggestion is right and should be merged into step 6 now rather than proposed a second time.
- **Account-level session rate limits, not agent work, dominated this run's wall clock.** Two resets (6am and 12pm Asia/Tehran) cost roughly 8 of the run's ~11 hours in pure waiting, split across three separate kill/resume cycles (QA twice, backend once). None of this is a `develop-feature` process problem — it is an operating-environment constraint the process has no lever over — but it is worth naming plainly rather than folding into "guardrails took two rounds," since the actual compute cost of this run was a small fraction of its calendar time.
- **What worked well, worth keeping**: debugging failures directly (a live `curl` round-trip, a throwaway Playwright script against the real running stacks) before routing anything let every routing message this run hand the fixing agent an exact field name, an exact file and line, and a confirmed root cause rather than a symptom — every routed fix landed correctly on its first real attempt (the two mid-fix rate-limit kills were account-level interruptions, not wrong diagnoses). This is the same lesson the previous retro drew from QA's `ASSUMPTION`-commented locators: precise, evidence-backed dispatch prompts are what keep the three-strike cap from ever mattering.

## Suggested improvements

1. **Add to `develop-feature`'s step 2/3 guidance**: *"If QA (step 2) and backend (step 3) are dispatched in parallel rather than sequentially, the step-1 plan must specify the exact field names of every new request/response body it introduces, not just which endpoints and problem types exist — otherwise QA's Technical layer and backend's DTOs are two independent guesses at the same contract with nothing to reconcile them before guardrails."* *Observation source: "Where the step-1 plan was wrong," first finding.*

2. **Actually merge the previous retro's suggestion #2 into step 5's dispatch template**, rather than re-suggesting it: *"Before designing markup, read `acceptance-tests/screenplay/ui/<feature>-page.ts` and its companion `<feature>-form.ts` in full — every locator QA wrote is commented `ASSUMPTION` about markup that didn't exist yet. Match your accessible names/roles to them where the assumption is reasonable; where you deliberately build something different, say so and why in your report."* *Observation source: "Friction," second bullet — this is the second run in a row this exact gap caused a routed fix.*

3. **Actually merge the previous retro's suggestion #3 into step 6**, rather than re-suggesting it: *"If the agent a failure is routed to isn't reachable in `ListAgents` (or `SendMessage` reports no transcript — dispatches can be killed by account-level session limits, not just task failures), dispatch a fresh one with full context of exactly what's already on disk and what remains, rather than waiting or resuming a dead reference."* *Observation source: "Friction," third bullet — independently re-derived three times in one run, which is itself the evidence this belongs in the skill rather than in a retro file.*
