## The shape of the run

Every step ran (1 through 9), auto mode's documented replacements throughout: step 1 stated the plan and proceeded; step 2/3 dispatched in parallel (QA and backend, both pure/generic-enough to plan against a pinned field/enum contract up front); step 5 built a full UI slice on the orchestrator's own read of the Gherkin as report-viewing (screen-first), independent of which door QA's own automation happened to use; step 6 needed two extra routed-fix cycles beyond the first `run-guardrails` failure; step 8 committed and pushed without confirmation.

One step-2/3 dispatch (qa-engineer) was killed mid-verification by an account-wide session/usage rate limit, not by any fault of its own — its code changes were already correctly on disk when this happened. Per the documented protocol, a fresh qa-engineer agent was dispatched with a full diagnosis rather than attempting to resume the dead one, which worked cleanly.

## Where the step-1 plan was wrong

**1. The actor-tracking design was under-specified at exactly the point that mattered, and it produced the run's worst bug.** The plan said: "a new framework-level `ActorContextMiddleware`, not by touching any other module... exposes the current userId through the request's continuation... the projector resolves the display name via `DisplayNameProvider`." That is correct in shape, but it doesn't say anything about *how the middleware-applied instance and the DI-injected instance relate* — and in NestJS they are not guaranteed to be the same object. The backend agent built exactly what the plan asked for, and it silently no-op'd on every single request: `use()` ran on one `ActorContextMiddleware` instance and populated *its* `AsyncLocalStorage`, while `AuditLogProjector`'s injected `ActorContext` (resolved via `ActorContextModule`'s `useExisting` binding) was a *different* instance with its own, permanently-empty `AsyncLocalStorage`. Every unit test passed (they construct the class directly, so there was only ever one instance in each test). The bug was invisible until a real acceptance run drove real HTTP requests through the real DI container, and even then it was silent — the projector's own `catch` block (also specified in the plan, for the right reason: "an audit-projection failure must never fail the underlying business command") logged a `warn` and swallowed it, and the test stack runs `LOG_LEVEL=silent`. The fix (a module-scope `AsyncLocalStorage` shared by however many instances Nest constructs) is one line different from what the plan described, but the plan's phrasing gave no reason to expect the two-instance trap, and nothing short of a live run against the real DI graph would have caught it — this is worth remembering as a class of NestJS pitfall (any port bound via `useExisting` to a class that is *also* applied as middleware) rather than a plan-writing mistake to avoid next time by writing more words.

**2. The UI-surface call and QA's own door choice diverged, and both were probably right on their own terms.** The plan reasoned "viewing a report is inherently a screen-first UX, like the recent BOM dashboard" and committed to building a full frontend slice. QA, dispatched with the same behavioural brief, independently concluded (per `acceptance-tests/CLAUDE.md`'s grammatical-voice rule: "a backend rule with no screen as the point stays on the API door even when phrased actively") that every scenario here is API-only, and wrote a purely API-driven Technical layer with no `screenplay/ui/` at all. Both calls stayed in place — the frontend was still built, and the acceptance suite still exercises the feature entirely over HTTP — and nothing broke as a result, but it means the acceptance suite does not exercise the UI at all for a feature that has one. The plan should have settled this explicitly for QA rather than leaving it to independently re-derive from the same ambiguous behavioural brief: either "build UI, but automate API-only, because X" or "automate through the UI for at least the list scenario."

**3. The filter's `to`-is-day-inclusive semantics, called out explicitly in the plan, needed zero correction.** This is the inverse of the two items above and worth recording as a positive: the plan noticed, from reading the Gherkin's own example table alone (an event at `10:00` passing a `to` filter of `00:00` the same date), that `to` had to mean "inclusive of that whole calendar day" rather than an exact-instant upper bound, and said so explicitly to backend. Backend implemented it correctly on the first pass, and it was never a source of a guardrails failure. Front-loading that one inference paid for itself.

Routed to qa-engineer (resumed). That resume's own live-verification attempt was killed by an account-wide rate limit before it could report — but its two fixes were already correctly applied and typechecked on disk. Re-verifying directly myself found both fixes correct but surfaced a **third**, previously undiagnosed failure: the full-list ordering scenario, off by exactly the two events `ProductCompositionFactory` auto-creates when row 3's product registration names a component/material that doesn't exist yet — a side effect that lands *inside* the tracked top-10 window rather than safely past it, unlike the fixture's other (correctly backdated) noise. Root-caused this myself by reading the fixture code, then dispatched a **fresh** qa-engineer (the old one's session no longer existed) with the full diagnosis already done. It applied the fix (pre-registering two more throwaway component/material names at the existing `NOISE_INSTANT`) and confirmed live: `12 successful, 12 total`.
- **Round 3 (full `make run-guardrails`, final)**: all nine checks green, full 174-scenario suite, exit 0.

Three distinct defects were found and routed across the two rounds — none of them survived more than one routed-fix cycle (the failure cap in step 6 was never actually approached), but the *feature* needed three separate fix cycles because each guardrails/verification pass reliably uncovered exactly one new defect rather than all of them at once. That pattern — fix one thing, re-verify, find the next thing underneath it — is worth naming plainly rather than reading as "3 rounds to fix 1 bug."

## Friction

- **`cucumber.cjs`'s `paths: ['specs/**/*.feature']` silently overrides a positional feature-path argument.** Every attempt (mine and both qa-engineer dispatches') to run `npx cucumber-js specs/audit-logging/viewing-audit-log.feature` for a fast, scoped check instead ran the full 174-scenario, ~7.5-minute suite. This happened at least five times across the run (my two direct diagnostic runs, the final two `make run-guardrails` invocations, and the fresh qa-engineer's own verification), costing on the order of 35-40 minutes of wall-clock that a working scoped-run command would have cut to under a minute each. Belongs in `acceptance-tests/CLAUDE.md`'s Commands section, next to the other `npx cucumber-js` examples already listed there.
- **Long command output captured via the background-task mechanism is tail-truncated with no visible warning.** My first two attempts to read a failing cucumber run's actual assertion output (buried ~300 lines into a 17,000+-line log) got back only the last ~300-400 lines of stdout, with no indication anything earlier had been dropped — I only found this by noticing the returned line count didn't match a `wc -l` on the same file written to disk. Explicitly redirecting to a file (`> /path/on/disk`) and grepping that was the only reliable way to inspect it; worth defaulting to that pattern for any command expected to produce more than a couple hundred lines, rather than discovering the truncation after the fact.
- **A subagent that starts its own background shell command is never woken by that command's completion.** Only the top-level orchestrator session receives task-notifications; a dispatched agent (qa-engineer, here) that backgrounds a long verification run and ends its turn produces a stale, non-answer final report ("I'll wait for the background task to finish and notify me") because nothing will ever resume it for that reason. Every dispatch prompt that asks an agent to run a multi-minute verification command should say explicitly "run this in the foreground, not backgrounded" — this belongs in the `/develop-feature` skill itself (the guardrails-routing dispatches), not just something the orchestrator has to remember ad hoc.

## Suggested improvements

1. **Observation**: friction item 1 (path-scoping). **Section**: Friction. **Change**: add a line to `acceptance-tests/CLAUDE.md`'s Commands section, immediately after the existing `npx cucumber-js specs/authentication/logging-in.feature` example: "A positional feature path is silently ignored by `cucumber.cjs`'s own `paths: ['specs/**/*.feature']` — the whole suite runs regardless. To scope a run, [find and document the actual working incantation, e.g. a temporary `@only`-style tag, `--profile`, or editing `paths` locally] rather than assuming the CLI argument alone narrows it."
2. **Observation**: plan-wrongness item 1 (the two-instance `ActorContextMiddleware` bug). **Section**: Where the step-1 plan was wrong. **Change**: in `/develop-feature`'s step-3/4 backend dispatch template, add a standing caution wherever a plan asks for "a port bound via `useExisting` to a class that is also applied as Nest middleware": "confirm live, against the real DI container and a real HTTP request, that the middleware-constructed instance and the DI-injected instance are the same object — Nest does not guarantee this, and a unit test that constructs the class directly will never catch a mismatch."
3. **Observation**: friction item 3 (subagent can't be woken by its own background job). **Section**: Friction. **Change**: in `/develop-feature`'s step 6 ("have the fixing agent confirm its own fix against a targeted, live check"), append: "instruct the agent explicitly to run that live check in the foreground, never backgrounded — a dispatched agent has no mechanism to be resumed when a background job of its own finishes, and will otherwise end its turn on a stale non-answer."
4. **Observation**: plan-wrongness item 2 (UI-surface vs. QA's own door choice diverging). **Section**: Where the step-1 plan was wrong. **Change**: in `/develop-feature`'s step-1 UI-surface resolution, when the orchestrator decides "UI-voiced" from context rather than from an explicit active `When`, add a line to the QA dispatch stating that decision outright — e.g. "This is being built with a full frontend slice; automate through the API is fine if that's what the grammatical-voice rule calls for, but say so explicitly in your report rather than leaving the orchestrator to infer it" — so the divergence is visible immediately rather than only noticed while writing this retro.
